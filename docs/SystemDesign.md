## 1. 项目整体介绍

### 1.1 项目背景

在高校校园中，二手物品交易需求旺盛。毕业生离校、学期更替、宿舍搬迁等场景催生了大量闲置物品的流转需求。然而，目前校园内二手交易主要依赖微信群、QQ 群、贴吧等非结构化渠道，存在信息分散、匹配效率低、交易信任成本高等问题。因此，一个面向高校师生的专用二手交易平台具有明确的实用价值。

### 1.2 项目目标

CampusTrade 旨在为高校师生提供一个结构化的二手交易平台，实现以下目标：

- 提供一个集中的商品信息发布与浏览渠道
- 建立规范的交易流程，降低交易风险
- 通过管理员审核机制保障商品信息的真实性和合规性
- 支持商品收藏、状态追踪等辅助功能，提升用户体验
- 以软件工程规范流程驱动开发，作为课程实践项目

### 1.3 核心价值

- **信息聚合**：将分散在各社交渠道的二手信息集中管理
- **信任保障**：管理员审核 + 实名校园环境，降低虚假信息风险
- **流程规范**：商品与订单的双状态机设计，确保交易状态清晰可追溯
- **工程实践**：以 Contract First 和前后端分离为核心理念，覆盖完整开发流程

### 1.4 技术架构

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 前端框架 | Next.js (React) | 服务端渲染 + 客户端交互 |
| 样式方案 | TailwindCSS | 原子化 CSS，快速构建 UI |
| 后端框架 | Midway.js | 基于 TypeScript 的 Node.js 企业级框架 |
| ORM | TypeORM | 支持 TypeScript 的 ORM 框架 |
| 数据库 | MySQL | 关系型数据库存储核心业务数据 |
| 接口规范 | OpenAPI 3.0 | Contract First，前后端并行开发 |
| 容器化 | Docker / Docker Compose | 标准化部署 |

## 2. 用户角色设计

系统定义三种用户角色，权限层次逐级递增。

### 2.1 Guest（未登录访客）

- 浏览商品列表与商品详情
- 按分类筛选商品
- 搜索商品
- 访问首页和公开页面
- **不能** 发布商品、收藏、下单

### 2.2 User（已登录用户）

- 拥有 Guest 的所有权限
- 发布商品（需通过管理员审核后方可上架）
- 编辑、删除自己的商品
- 收藏 / 取消收藏商品
- 购买其他用户发布的商品（不能购买自己发布的商品，buyerId != sellerId）
- 查看自己的订单列表与订单详情
- 管理个人资料

### 2.3 Admin（管理员）

- 审核商品（通过 / 驳回）
- 商品强制下架
- 查看审核记录

## 5. 用户业务流程

### 5.1 访客浏览流程

```
进入首页 → 浏览商品列表 → 点击商品 → 查看商品详情
    │                              │
    └── 按分类筛选 ────────────────┘
    │
    └── 搜索商品
```

访客无需登录即可浏览商品信息和列表，但无法进行发布、收藏、下单等操作。如需进一步操作，将引导至登录页面。

### 5.2 用户购买流程

```
登录 → 浏览商品 → 进入商品详情 → 点击"立即购买"
    → 创建订单 → 订单状态: Pending（等待卖家确认）
    → 卖家确认交易 → 订单状态: Confirmed（等待买家确认收货）
    → 买家确认收货 → 订单状态: Completed
```

用户可以购买其他用户发布的商品，但不能购买自己发布的商品（buyerId != sellerId）。订单创建后，商品状态从 Approved 变为 Reserved，防止其他用户同时下单。

### 5.3 用户发布商品流程

```
登录 → 进入发布页面 → 填写商品信息（标题、描述、价格、分类、图片）
    → 提交审核 → 商品状态: PendingReview
    → 等待管理员审核
    → 审核通过 → 商品状态: Approved → 商品上架可见
    → 审核驳回 → 商品状态: Rejected → 用户可查看驳回理由，修改后重新提交
```

### 5.4 管理员审核流程

```
登录 → 进入管理后台 → 查看待审核商品列表
    → 查看商品详情
    → 审核操作：
        ├── 通过 → 商品状态: Approved → 商品上架
        └── 驳回 → 填写驳回理由 → 商品状态: Rejected → 退回给用户
```

## 6. 商品状态机

### 6.1 状态定义

| 状态 | 标识 | 说明 |
|------|------|------|
| 待审核 | PendingReview | 用户提交后等待管理员审核 |
| 已上架 | Approved | 审核通过，前台可见，可被下单 |
| 已预订 | Reserved | 已有订单关联，暂不可再被下单 |
| 已售出 | Sold | 交易完成，商品已售出 |
| 审核驳回 | Rejected | 审核失败，用户可修改后重新提交 |
| 已下架 | Removed | 用户主动下架或管理员强制下架 |

### 6.2 状态转换规则

```
PendingReview ──(审核通过)──────→ Approved
PendingReview ──(审核驳回)──────→ Rejected
Rejected ───────(修改后重新提交)──→ PendingReview
Approved ───────(用户下单)──────→ Reserved
Reserved ───────(取消订单)──────→ Approved
Reserved ───────(确认交易)──────→ Sold
Approved ───────(用户下架)──────→ Removed
Approved ───────(管理员下架)──────→ Removed
Reserved ───────(管理员下架)──────→ Removed
PendingReview ──(用户下架)──────→ Removed
Rejected ───────(用户下架)──────→ Removed
Sold ───────────(终态)─────────→ Sold
Removed ────────(终态)─────────→ Removed
```

### 6.3 转换规则说明

- 只有 Approved 状态的商品可以被下单
- 商品被下单后立即进入 Reserved 状态，防止超卖
- 订单取消后商品恢复为 Approved，可被再次下单
- 审核驳回后商品进入 Rejected 状态，用户可修改后重新提交审核
- Sold 和 Removed 为终态，不可逆转

## 7. 订单状态机

### 7.1 状态定义

| 状态 | 标识 | 说明 |
|------|------|------|
| 待确认 | Pending | 买家创建订单，等待卖家确认 |
| 已确认 | Confirmed | 卖家确认交易，等待买家确认收货 |
| 已完成 | Completed | 买家确认收货，交易完成 |
| 已取消 | Cancelled | 订单被取消 |

### 7.2 状态转换规则

```
Pending ────(卖家确认交易)──→ Confirmed
Pending ────(取消订单)──────→ Cancelled
Confirmed ──(买家确认收货)──→ Completed
```

### 7.3 订单与商品状态联动

| 订单操作 | 订单状态变化 | 商品状态变化 |
|----------|-------------|-------------|
| 创建订单 | → Pending | Approved → Reserved |
| 取消订单 | Pending → Cancelled | Reserved → Approved |
| 卖家确认交易 | Pending → Confirmed | Reserved（不变） |
| 买家确认收货 | Confirmed → Completed | Reserved → Sold |

订单取消时，商品自动恢复为 Approved 状态，释放购买资格。订单完成后，商品进入 Sold 终态。

### 8.1 User（用户）

| 字段 | 作用 |
|------|------|
| id | 用户唯一标识 |
| username | 用户昵称，前台展示 |
| email | 登录凭证，唯一 |
| password | 登录密码，加密存储 |
| avatar | 头像图片路径 |
| phone | 联系方式 |

| isActive | 账号是否被禁用 |
| createdAt | 注册时间 |
| updatedAt | 信息更新时间 |

**关系**：User 与 Goods 为一对多关系（一个用户可发布多件商品）；User 与 Favorite 为一对多关系（一个用户可收藏多件商品）；User 与 Order 为一对多关系（一个用户可创建多个订单）。

### 8.2 Goods（商品）

| 字段 | 作用 |
|------|------|
| id | 商品唯一标识 |
| title | 商品标题 |
| description | 商品描述 |
| price | 商品价格 |
| images | 商品图片路径列表 |
| status | 商品状态（PendingReview / Approved / Reserved / Sold / Rejected / Removed） |
| version | 乐观锁版本号，用于并发控制 |
| userId | 发布者 ID，关联 User |
| categoryId | 分类 ID，关联 Category |
| createdAt | 发布时间 |
| updatedAt | 信息更新时间 |

**关系**：Goods 属于 User（多对一）；Goods 属于 Category（多对一）；Goods 与 Favorite 为一对多关系；Goods 与 Order 为一对多关系。

### 8.3 Category（分类）

| 字段 | 作用 |
|------|------|
| id | 分类唯一标识 |
| name | 分类名称 |
| description | 分类描述 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |

**关系**：Category 与 Goods 为一对多关系（一个分类下可有多件商品）。

### 8.4 Favorite（收藏）

| 字段 | 作用 |
|------|------|
| id | 收藏记录唯一标识 |
| userId | 用户 ID，关联 User |
| goodsId | 商品 ID，关联 Goods |
| createdAt | 收藏时间 |

**关系**：Favorite 联合关联 User 和 Goods，一个用户对同一件商品只能收藏一次（联合唯一约束）。

### 8.5 Order（订单）

| 字段 | 作用 |
|------|------|
| id | 订单唯一标识 |
| userId | 买家 ID，关联 User |
| goodsId | 商品 ID，关联 Goods |
| status | 订单状态（Pending / Confirmed / Completed / Cancelled） |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |

**关系**：Order 属于 User（多对一）；Order 属于 Goods（多对一）。

### 8.6 ReviewRecord（审核记录）

| 字段 | 作用 |
|------|------|
| id | 审核记录唯一标识 |
| goodsId | 商品 ID，关联 Goods |
| adminId | 审核人 ID，关联 User |
| action | 审核动作（approved / rejected） |
| reason | 驳回理由（审核通过时可为空） |
| createdAt | 审核时间 |

**关系**：ReviewRecord 关联 Goods 和 User（管理员），记录每次审核操作的详细信息。

### 8.7 实体关系总览

```
User ──1:N──→ Goods
User ──1:N──→ Favorite
User ──1:N──→ Order
Category ──1:N──→ Goods
Goods ──1:N──→ Favorite
Goods ──1:N──→ Order
Goods ──1:N──→ ReviewRecord
User (Admin) ──1:N──→ ReviewRecord
```

## 11. 架构设计决策

### 11.1 前后端分离

采用前后端分离架构，前端 Next.js 作为独立服务运行，后端 Midway.js 提供 RESTful API。前后端通过 HTTP 通信，职责清晰，可独立开发、测试和部署。

### 11.2 Contract First

使用 OpenAPI 3.0 作为接口契约的唯一事实来源。在编码之前先定义接口规范，前后端团队（或同一开发者）可依据契约并行开发，减少联调成本。契约文件同时作为 API 文档自动生成的基础。

### 11.3 审核机制

所有商品发布后必须经过管理员审核才能上架展示。该机制保障了商品信息的真实性和合规性，降低虚假信息风险。审核记录通过 ReviewRecord 实体持久化，支持审计追溯。

### 11.4 双状态机

商品和订单各自拥有独立的状态机，并通过联动规则保持一致性。状态机设计确保了业务流程的规范性，防止非法状态跳转。每个状态转换都有明确的触发条件和前置状态。

### 11.5 Reserved 防止超卖

商品被下单后立即从 Approved 转变为 Reserved，而非等到订单确认才锁定。这样在并发场景下，同一商品无法被第二个用户下单，从根本上防止超卖问题。订单取消时商品恢复为 Approved，释放购买资格。

### 11.6 Version 乐观锁

在 Goods 表中引入 version 字段，用于商品抢购场景的并发控制。当多个请求同时操作同一条商品记录时，通过版本号校验确保数据一致性。更新操作在 WHERE 条件中检查 version 值，若版本号不匹配则更新失败，由业务层进行重试或报错处理。
