## 1. 项目概述

### 1.1 项目目标

CampusTrade 是一个面向高校师生的校园内二手交易平台，旨在解决校园场景下二手物品信息分散、交易信任成本高的问题。平台提供商品浏览、搜索、发布、收藏、购买及管理员审核等核心功能，帮助在校师生便捷地进行二手物品流转。

### 1.2 用户范围

- **在校学生**：需要在校园内发布和寻找二手物品的学生群体
- **教职工**：有二手物品交易需求的教职工
- **平台管理员**：负责审核商品信息、维护平台秩序的管理人员

### 1.3 核心业务价值

- **信息聚合**：将分散在各社交渠道的二手信息集中到一个平台，降低信息查找成本
- **信任保障**：通过管理员审核机制过滤虚假信息和违规内容，提升交易安全性
- **流程规范**：商品从发布到售出的完整状态流转，确保交易过程清晰可追溯
- **操作简便**：简化二手交易流程，降低使用门槛

## 2. 用户角色

### 2.1 Guest（未登录访客）

Guest 是未登录系统的用户，拥有平台最基础的浏览权限：

- 浏览商品列表与商品详情
- 按分类筛选商品
- 搜索商品
- 访问首页和公开页面

Guest **不能** 进行发布商品、收藏商品、创建订单等操作。如需进行以上操作，需先注册并登录。

### 2.2 User（已登录用户）

User 是已完成注册并登录的普通用户，拥有完整的个人交易功能：

- 拥有 Guest 的所有权限
- 发布商品（需通过管理员审核后方可上架展示）
- 编辑和删除自己发布的商品
- 收藏和取消收藏商品
- 购买其他用户发布的商品（不能购买自己发布的商品）
- 查看自己的订单列表与订单详情
- 管理个人资料（头像、联系方式等）

### 2.3 Admin（管理员）

Admin 是平台的管理人员，负责维护平台秩序：

- 审核商品（通过或驳回）
- 商品强制下架
- 查看审核记录

## 4. Business Rules

### BR-001 发布权限

只有登录用户（User 角色及以上）可以发布商品。Guest 没有发布权限。

### BR-002 审核前置

商品发布后必须经过管理员审核通过（Approved）才能在前台展示。未通过审核的商品（PendingReview / Rejected / Removed）对除管理员外的用户不可见。

### BR-003 禁止自买自卖

用户不能购买自己发布的商品。系统在创建订单时校验 buyerId 与 sellerId 是否相等，若相等则拒绝创建订单。

### BR-004 商品状态约束

只有处于 Approved 状态的商品可以创建订单。其他状态（PendingReview、Rejected、Reserved、Sold、Removed）的商品均不可下单。

### BR-005 商品独占

商品进入 Reserved 状态后，不能被其他用户购买。该约束确保同一商品在同一时间只能被一个有效订单占用。

### BR-006 终态不可逆

商品进入 Sold 或 Removed 状态后，不可再恢复为其他状态。Rejected 状态的商品可修改后重新提交审核，不属于终态。

### BR-007 管理员权限

管理员有权强制下架任何状态的商品，无需经过商品发布者同意。

## 5. Edge Cases

### EC-001 用户重复收藏同一商品

用户对同一商品连续点击两次收藏。

预期行为：第一次点击收藏成功，第二次点击应提示"已收藏"或忽略重复操作。系统应通过联合唯一约束确保同一用户对同一商品只能有一条收藏记录。

### EC-002 用户购买已被购买的商品

用户A打开商品详情页时商品为 Approved，此时用户B先完成了下单。用户A点击"立即购买"。

预期行为：系统在创建订单时检查商品状态，发现商品已被 Reserved，拒绝创建订单并提示"商品已被购买"。

### EC-003 用户删除不存在的商品

用户尝试删除一个已被删除或不存在的商品。

预期行为：系统返回商品不存在或已删除的提示，不执行任何操作。

### EC-004 订单重复提交

用户快速连续点击"立即购买"按钮，导致多次提交订单请求。

预期行为：系统应通过幂等性或状态校验，确保同一商品只能创建一笔有效订单。重复提交应被拒绝。

### EC-005 管理员审核已审核商品

管理员对已处于 Approved、Rejected 或 Removed 状态的商品再次执行审核操作。

预期行为：系统校验商品当前状态，若商品已不在 PendingReview 状态，拒绝审核操作并提示"商品已审核"。

### EC-006 并发购买同一商品

用户A和用户B同时发起对同一商品的购买请求，两个请求在时间上高度重叠。

预期行为：系统通过数据库层面的乐观锁（version 机制）或条件更新确保只有一个请求能成功创建订单，另一个请求失败并提示"商品已被购买"。

- 商品列表页支持分页查询，单页默认展示不超过 20 条商品
- 常规接口请求应在合理时间内返回响应
- 商品图片应进行适当压缩，避免页面加载过慢

### 6.2 安全

- 用户密码不得明文存储，必须使用加密算法（如 bcrypt）处理
- 登录接口需验证用户身份，未登录用户无法访问需鉴权的接口
- 用户只能操作自己的资源（商品、订单、收藏），无法越权访问他人数据

### 6.3 可靠性

- 商品和订单的状态转换必须严格遵循状态机定义，不允许非法状态跳转
- 并发场景下保证数据一致性，不出现超卖或重复订单

### 6.4 可维护性

- 前后端接口遵循 OpenAPI 3.0 契约规范，接口变更需同步更新契约文件
- 代码遵循统一的编码规范，保持可读性
